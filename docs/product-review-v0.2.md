# 刻忆 产品体验审视与迭代方案（V0.2）

> 以高级产品经理视角，对 V0.1 的使用体验、界面与交互做一次系统审视，给出设计原则、本次落地的改动和后续迭代路线。
> 本文随 V0.2 一起提交，标 ✅ 的已在本版实现。

## 一、V0.1 现状诊断

定位是对的：只做一件事（记住重要日子、提前提醒），本地优先，托盘常驻，不需要账号。
问题集中在"用的时候"的细节，按用户旅程逐段看：

| 旅程 | 问题 | 影响 |
| --- | --- | --- |
| 打开窗口 | 没有"今天是几号、农历几号"的锚点；看不出今天 / 本周有几件事，要自己扫一遍列表 | 每次打开都要重新定位，和"一目了然"的承诺不符 |
| 看列表 | 五种类型只用灰色文字标签；忌日、节日、其他没有视觉区分；倒数数字和日期的层次接近 | 扫视效率低，重要的那一条不跳出来 |
| 收到提醒之后 | 提前一个月提醒后礼物已经买好，一周前、三天前仍会再弹 | 提醒变打扰，长期会让用户关掉提醒 |
| 增删改 | 保存、删除都没有回声；删除不能撤销；编辑到一半误按 Esc 或点到遮罩直接丢失 | 不放心，误操作成本高 |
| 键盘用户 | 没有任何快捷键，对话框焦点不受控 | 熟练用户效率低 |
| 外观 | 只能跟随系统，不能单独选浅色 / 深色；窗口大小位置每次重置 | 小但高频的摩擦 |
| 升级 | 没有任何新版本感知，只能自己去 GitHub 看 | 老用户停留在旧版，修复和新功能触达不到 |

## 二、设计原则（本次与后续都遵守）

1. **一眼看懂**：顶部先回答"今天几号、有几件事"，再看列表。
2. **少打扰、可闭环**：每次提醒都能被用户"收口"（已准备），而不是只能关掉提醒。
3. **每个操作有回声**：保存 / 删除 / 标记都有轻提示，可撤销的就提供撤销。
4. **本地优先，联网只为更新**：数据永远不出本机；唯一的网络请求是检查更新，且用户可关闭。
5. **克制的视觉**：暖纸色底 + 朱砂红一个主色，类型色只做区分不做装饰，深色模式成对设计。

## 三、本次落地（V0.2）

### 体验与视觉

| 改动 | 说明 |
| --- | --- |
| ✅ 今日锚点与概览条 | 首页顶部显示"10月16日 周五 · 农历九月初七"，右侧统计今天 / 7 天内 / 30 天内各几件、共几条；有事的统计高亮 |
| ✅ 列表信息层次 | 倒数数字放大并用等宽数字；今天用主色实心块、7 天内用金色、30 天内用灰色；五种类型各有图标与颜色（生日朱砂、纪念日金、忌日蓝灰、节日青、其他灰） |
| ✅ 图标系统 | 自绘线性 SVG 图标替换"♥ ＋ ×"等文字符号，按钮和表单统一带图标 |
| ✅ 分组标题吸顶 | 滚动时"今天 / 7 天内 / 30 天内 / 更晚"始终可见 |
| ✅ 轻提示与撤销 | 保存 / 添加 / 标记有 toast；删除后 6 秒内可撤销（原样恢复，不会重复弹已发过的提醒） |
| ✅ 编辑保护 | 有改动时按 Esc / 点遮罩会先问"放弃修改？"；删除改为底栏内二次确认 |
| ✅ 键盘 | `Ctrl+N` 添加、`/` 或 `Ctrl+F` 搜索、`Ctrl+,` 设置、`Esc` 关闭、`Ctrl+Enter` 保存；对话框内 Tab 循环、关闭后焦点还原 |
| ✅ 主题 | 设置里可选跟随系统 / 浅色 / 深色，即选即生效 |
| ✅ 窗口记忆 | 记住窗口大小、位置与最大化状态 |
| ✅ 搜索框 | 带图标与一键清空；筛选无结果时提供"清除筛选" |
| ✅ 空状态 | 新增"已有备份？到设置里导入"的次要路径 |

### 功能

| 改动 | 说明 |
| --- | --- |
| ✅ "已准备"闭环 | 一个月内的条目可标记"已准备"：之后的提前提醒不再打扰，**当天仍提醒一次**；明年自动恢复；改日期会清除标记。设计上选择保留当天提醒，是因为"准备好礼物"和"当天记得说"是两件事 |
| ✅ 自定义提前天数 | 常用 30 / 7 / 3 / 1 / 当天之外，可填 1–60 天内任意天数 |
| ✅ 应用内更新 | 打开窗口时、托盘菜单"检查更新"、设置里手动，以及后台每 6 小时检查 GitHub Releases；发现新版本顶部横幅提示，点"立即更新"下载、校验签名、静默安装并自动重启；"稍后"24 小时内不再提示；只在托盘运行时发现新版本会弹一条通知。可在设置里关闭自动检查 |
| ✅ 打开数据目录 | 设置里一键在资源管理器定位数据文件 |
| ✅ 托盘菜单 | 新增"检查更新…" |

### 工程

| 改动 | 说明 |
| --- | --- |
| ✅ CI | 核心单测 + clippy、农历逐日对照、前端类型检查 / 单测 / 构建、版本号一致性检查；Windows 上 clippy 并试打包 |
| ✅ 发版 | 推标签 `v*` 或手动运行：校验版本与密钥 → 构建并签名 → 生成 `latest.json`、`SHA256SUMS.txt` → 创建 Release；带 `-` 的标签标为预发布，不会推给现有用户 |
| ✅ 版本管理 | `npm run version:set -- 0.3.0` 一次改齐四处版本号 |

## 四、后续迭代路线

按"用户价值 ÷ 实现成本"排序，并标出前置条件。

### Next（V0.3，提醒体验继续收口）

| 功能 | 价值 | 说明与风险 |
| --- | --- | --- |
| 通知上的"稍后提醒 / 已准备"按钮 | 不用打开窗口就能闭环 | Windows Toast 支持按钮，但 tauri-plugin-notification 对 Windows 按钮回调的支持尚不完整，可能需要直接调用 WinRT；先做"点击通知打开窗口并定位到该条" |
| 重要度分级 → 提醒强度 | 核心人（父母、伴侣）和泛关系（客户）需要的打扰程度完全不同 | 两档即可：重点（额外在前 3 天每天提醒、首页置顶、托盘提示优先）/ 普通。在数据模型加 `importance` 字段，提醒阶段逻辑复用现有 offsets |
| 批量导入 | 第一次录入是最大流失点 | 支持 CSV（姓名、公历 / 农历日期、类型），模板可下载；从 Windows 通讯录 / 手机导出的生日字段做映射 |
| 今天的"回顾"视图 | 当天打开时直接给出"今天要做什么" | 今天分组展开备注全文，显示去年备注（如"去年送了围巾"） |

### Later（V0.4+，扩展）

| 功能 | 说明 |
| --- | --- |
| AI 祝福语 | 根据关系、年龄、备注生成 3 条可编辑的祝福语。需要联网与 API Key，必须做成可选且明确告知；建议放在"今天"条目的详情里，一键复制 |
| 数据同步 | 先做"同步文件夹"方案（把数据文件放到 OneDrive / 坚果云目录，多端合并已有 `merge` 逻辑），零后端成本；再评估云账号 |
| 移动端 / 浏览器插件 | `daymark-core` 不依赖 Tauri，可编译为 WebAssembly 复用农历与提醒逻辑；移动端优先考虑 Tauri Mobile |
| 农历节气、生肖、年龄两种算法 | 虚岁 / 周岁切换；节气提醒（如清明）对忌日类用户有价值 |
| 多语言 | 界面文案已集中在组件内，抽到字典即可；繁体中文优先 |

### 不做

- 社交 / 分享功能：与"私密、本地"的定位冲突。
- 日历视图：主场景是"提前知道"而非"查某天"，列表分组已经够用；若做也只做月视图的只读模式。

## 五、成功指标（建议埋在本地、不上报）

- 提醒触达率：实际发出的提醒 / 应发提醒（`fired` 对比 `due`），目标 > 95%。
- "已准备"使用率：被标记的条目 / 一个月内的条目。能反映闭环是否被理解。
- 更新到达率：发布 7 天后运行新版本的比例（只能从 Release 下载量粗估）。
- 第一周留存：装好后 7 天内条目数 ≥ 3 的用户比例。

## 六、风险与待确认事项

| 风险 | 应对 |
| --- | --- |
| 安装包未做代码签名，SmartScreen 会拦 | 更新包已用 minisign 签名保证不被篡改；代码签名证书待预算决定 |
| 国内访问 GitHub 不稳定 | 更新检查失败只静默重试，不打扰；后续可加镜像端点（`endpoints` 支持多个，按顺序尝试） |
| 更新签名私钥只有一份 | 丢失则需换公钥并让用户手动装一次，见 docs/development.md 的保管说明 |
| 开机自启参数下更新后重启 | 已处理：安装程序重启后即使带 `--autostart` 也会弹出窗口并提示"已更新" |
